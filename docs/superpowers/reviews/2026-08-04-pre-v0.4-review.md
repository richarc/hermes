## Summary

The codebase is in good shape: the pure libraries are well factored and
genuinely well tested, the tricky parts (chart lifecycle, citation rule
ordering, inline-mark doubling, stale-response generation guards) are correct
*and* carry comments explaining why. The problems are concentrated in three
places — one severe performance defect in the citation path, one data-safety
gap in the save path, and a set of structural issues that the three remaining
v0.4 items will each make worse if they land first.

Ranked, with the ordering argued at the end:

| # | Finding | Severity |
|---|---------|----------|
| P1 | citeproc engine rebuilt on every render: 240–500 ms stall every 250 ms while typing | **High** |
| D1 | Document saves are not atomic — a failed write destroys the user's file | **High** |
| A1 | Settings don't generalise, and v0.4 adds two more | Medium |
| P2 | 5.8 MB eager main chunk; vega and all five CSL styles load unconditionally | Medium |
| D3 | LaTeX markup in `.bib` fields renders as literal HTML in the References list | Medium |
| A3 | Scroll sync needs source-position anchors the render path doesn't emit | Medium |

| Q1–Q4, T1–T2 | Go nits, silent failures, path scope, test gaps | Low |

## Data safety and correctness

### D1. Document saves are not atomic — **High**

`documentservice.go:63`

```go
if err := os.WriteFile(path, []byte(content), 0o644); err != nil {
```

`os.WriteFile` opens with `O_TRUNC`: the user's file is emptied first, then
rewritten. If the write fails partway — disk full, the app killed, power loss —
the paper is left truncated and there is no backup. For an editor whose whole
purpose is holding someone's thesis, this is the highest-consequence line in
the repo.

Fix: write to a temp file in the *same directory* (same filesystem, so the
rename is atomic), `f.Sync()` it, then `os.Rename` over the target. Preserve
the existing file's mode when it already exists, rather than forcing `0o644`.

The same non-atomic pattern applies to `recents.json` (`:184`) and
`settings.json` (`:143`). Those are lower stakes — both readers already fall
back to a default on a parse error — but the same helper covers all three.

### D2. `addRecent` is a lock-free read-modify-write — **Low**

`documentservice.go:170-186` does read file → dedupe → prepend → truncate →
write file with no synchronisation. Wails runs binding calls concurrently: the
message processor tracks simultaneously-running calls in a mutex-guarded
`runningCalls` map and supports cancelling one while others proceed
(`messageprocessor_call.go:76-91`). So two overlapping `Save`/`OpenPath` calls
can interleave and drop an entry.

`dirty` is already an `atomic.Bool` and the watcher has `watchMu`, so recents
is the one piece of shared mutable state left unguarded. A `sync.Mutex` around
the read-modify-write (shared with `ClearRecents`) closes it.

### D3. LaTeX markup in `.bib` fields renders as literal HTML — **Medium**

Measured. Given a real-looking entry:

```bibtex
title = {A \textbf{bold} claim about x <5 and y >10 with 50\% yield}
```

`parseBib` (`bibliography.ts:68`) currently returns:

```
A <span class="nocase"><b>bold</b></span> claim about x ¡5 and y ¿10 with 50% yield
```

Two things went wrong. The parser converted `\textbf` into HTML markup, and it
mapped `<` and `>` through LaTeX's OT1 encoding into `¡` and `¿`. citeproc then
escapes that markup correctly (see below), so the References list displays the
`<span class="nocase"><b>` tags **verbatim as text**, with the angle brackets
already mangled.

`\emph`/`\textit`/`\textbf` in titles are common in real `.bib` exports, so
this is reachable in normal use of the v0.3 headline feature.

`extractString` (`bibliography.ts:60-66`) takes the parser's rich-text output
as-is. `parse(text, { raw: true })` returns the untouched LaTeX source instead,
which is the other end of the spectrum. Neither is right on its own: CSL fields
*do* support `<i>`/`<b>`, so the higher-fidelity fix is to keep italics/bold
and drop the parser's `nocase` wrapper, which needs a short spike against the
parser's `markup` option (my first attempt at `markup: { bold: ['', ''] }` had
no effect, so the option name needs checking against the current version).

**Good news from the same probe:** HTML that reaches a CSL field *is* escaped
downstream. Injecting `Pwned <img src=x onerror="alert(1)"> end` directly as a
CSL title rendered as `Pwned &#60;img src=x onerror="alert(1)"&#62; end`. So
there is no injection path from a third-party `.bib` through
`Preview.svelte`'s `innerHTML`. That deserves a regression test to keep it
true (T2).

## Performance

### P1. The citeproc engine is rebuilt on every preview render — **High**

`citations.ts:67`

```ts
format(clusters) {
  const engine = new CSL.Engine(sys, style)   // ← per call
```

`format()` is called from `render()` (`renderer.ts:39`), which runs on every
debounced keystroke (250 ms, `App.svelte:58`). Measured with the project's own
vitest, warmed:

```
apa,                 1 cluster:   233.4 ms
apa,                20 clusters:  238.7 ms
apa,               100 clusters:  250.8 ms
chicago-author-date, 20 clusters: 502.5 ms
ieee,                20 clusters:   5.1 ms
```

The cost is almost entirely fixed engine construction — parsing the CSL XML.
Cluster processing is roughly 0.2 ms each; going from 1 to 100 clusters adds
17 ms while the floor sits at 233 ms. IEEE is cheap only because `ieee.csl` is
17 KB against `apa.csl` at 85 KB and `chicago-author-date.csl` at 168 KB.

For contrast, rendering a 300-paragraph document with 300 inline math spans and
no formatter takes **9.3 ms**. The markdown/KaTeX path is not the problem;
citeproc is.

In practice: writing a paper in the default APA style with any citations in it
blocks the webview's main thread for ~240 ms out of every 250 ms tick. Chicago
is worse than one full tick.

Fix: construct the engine once in `createCitationFormatter` and reset it
between passes. The reason it is rebuilt is presumably that citeproc-js
accumulates cluster state across `processCitationCluster` calls, so the reset
has to go through the engine's own path (`restoreProcessorState` /
`rebuildProcessorState`) and be *verified by test* rather than assumed — the
existing `citations.test.ts` cases for multi-cite ordering and
`submittedToOriginal` alignment are exactly the ones that would catch a bad
reset.

If no clean reset exists, the fallback is to take the whole citation pass off
the typing path: render the preview immediately without citations, then patch
formatted citations in from an idle callback. Either way this is the single
biggest responsiveness win available, and it should land **before** scroll sync
— a 240 ms stall every 250 ms will make sync feel broken no matter how the
mapping is implemented.

### P2. 5.8 MB eager main chunk — **Medium**

`dist/assets/index-Cf_2WEEo.js` is 5,831,519 bytes; `dist/` totals 8.3 MB
across 113 chunks. The lazy chunks are all CodeMirror language modes (good —
`@codemirror/language-data` is already doing its job). What is eager and
shouldn't be:

- **vega + vega-lite + vega-embed.** `charts.ts:1` imports `vega-embed`
  statically, and `Preview.svelte` imports `charts.ts` unconditionally, so
  every document pays for the chart engine whether or not it has a chart.
  `vega.min.js` alone is 516 KB and `vega-lite.min.js` 251 KB before their
  dependency graphs.
- **All five CSL styles, inlined as `?raw` strings** (`citations.ts:6-11`):
  apa 85 KB + chicago 168 KB + ieee 18 KB + vancouver 18 KB + harvard 11 KB =
  300 KB of XML in the bundle, of which one document uses at most one.
- **citeproc itself**, which a document with no `bibliography:` key never
  touches.

Fixes, in payoff-per-effort order:

1. `await import('vega-embed')` inside `embedChart`. `embedChart` is already
   async and the hydrator's generation guard (`charts.ts:63-68`) already
   handles an extra await, so the change is local.
2. Resolve the CSL style lazily — a dynamic `import()` keyed by style id — so
   an APA document doesn't ship Chicago. Note `STYLE_IDS` is exported and used
   for validation in `App.svelte:102`, so the id list needs to stay static
   while the *content* goes lazy.
3. Same treatment for citeproc, gated on the document naming a bibliography.

This is startup parse/compile latency rather than download latency, but it is
the same main thread the editor needs to become interactive.

### P3. Opening a document renders the preview twice — **Low**

`App.svelte:179-187`. `loadDocument` calls `editor.setContent()`, which fires
`onEditorChange` → schedules the debounced `updatePreview` — and then does its
own synchronous `html = render(...)`. 250 ms later the debounce renders
identical content again. With P1 unfixed that is a second 240 ms stall on every
open. `doNew()` (`:201-208`) has the same shape.

Fix: give `debounce` a `.cancel()` and call it from `loadDocument`/`doNew`, or
drop the synchronous render and let the debounce own the first paint.

### P4. Chart hydration is sequential — **Low, informational**

`charts.ts:49-72` awaits each `embed()` in turn, so N charts serialise N vega
compilations. Fine for two or three; noticeable for a results section with
eight. Worth leaving alone unless it shows up in practice — the sequential loop
is what keeps the ordering and generation guard simple.

## Architecture, with the remaining v0.4 items in view

### A1. Settings don't generalise, and v0.4 adds two more — **Medium**

One setting today (`printOrientation`) costs: a typed struct
(`documentservice.go:40-42`), a getter with its own defaulting logic
(`:116-130`), a validating setter that silently swallows three error paths
(`:132-149`), a dedicated `onOrientationChanged` callback field (`:32`), and a
wiring block in `main.go:87-91` that rebuilds the entire menu.

v0.4 adds a dark-theme choice (System/Light/Dark) and a scroll-sync toggle.
Both want persistence; the theme wants a menu radio group exactly like PDF
orientation; the roadmap explicitly asks whether scroll sync should persist
"as the PDF orientation setting does". Adding them the same way triples the
boilerplate and gives three near-identical rebuild callbacks.

Suggest: one `settings` struct holding all keys, a load-once/save-on-change
pair, and a single `settings:changed` event that both the frontend and the
menu rebuild subscribe to. This is worth doing **before** the two new settings,
not after.

### A2. `DocumentService` is the entire backend — **Low**

257 lines spanning file IO, native dialogs, recents, app settings, PDF
printing, bibliography reading, a filesystem watcher, and (via `zotero.go`) an
HTTP client — plus a `*application.WebviewWindow` injected from `main.go:69`.
Every exported method becomes frontend API, so the binding surface is 15
functions across five unrelated concerns, and `ExportPDF` hangs off a
*document* service.

Wails supports multiple registered services. Splitting into `DocumentService`
(open/save/recents), `SettingsService`, and `BibliographyService`
(read/watch/Zotero) would make the generated bindings self-documenting and give
each concern a focused test file. This is a refactor rather than a fix — better
at the v0.4/v0.5 boundary than mid-release.

### A3. Scroll sync needs source-position anchors the render path doesn't emit — **Medium**

The roadmap leaves the source→rendered mapping as an open question and worries
about height divergence (charts, math, tables). There is a standard answer, and
it dissolves that worry: markdown-it gives every **block** token a
`token.map` of `[startLine, endLine]`, so a `core.ruler` rule can stamp
`data-source-line` onto each top-level block during render. The preview then
binary-searches the nearest anchored element for a given editor line and
interpolates *between* anchors — so a chart that renders 40× taller than its
source block simply becomes a long interval between two known-correct
anchors, rather than an error term in a ratio.

Two current facts to design around:

- `Preview.svelte:11-14` replaces `container.innerHTML` wholesale on every
  render, so any anchor-derived scroll position must be re-derived after each
  pass rather than cached across them.
- With P1 unfixed the preview lags typing by up to half a second, which reads
  as broken sync regardless of how good the mapping is.

On the roadmap's other open questions, the code suggests: one-way
(editor drives preview) is the natural fit, because the editor is the only pane
with authoritative source positions; and persistence should ride on A1.

### A4. Dark theme touches four layers, one of them Go — **Medium**

- `public/style.css` hardcodes ~20 colours and pins `:root { color-scheme:
  light }` at `:5` with a comment explaining the deliberate opt-out.
- `Editor.svelte:60-72` adds no theme extension at all, so CodeMirror stays
  light unless one is added (`EditorView.theme` or `@codemirror/theme-one-dark`).
- The print block at `style.css:108-120` must keep rendering **light**
  regardless of app theme, or exported PDFs come out dark-on-dark. This is the
  easiest thing to miss.
- `main.go:57-65` hardcodes `BackgroundColour: NewRGB(255, 255, 255)` alongside
  `MacBackdropNormal`, so a dark-mode launch flashes white before the webview
  paints.

Suggest converting the stylesheet to custom properties on `:root` first (purely
mechanical, verifiable by eye), then wiring the choice through A1's settings
work, then the Go window colour last.

### A5. `App.svelte` is at the size where the next feature makes it worse — **Low**

407 lines owning: file lifecycle, dirty derivation, bibliography loading with
its reload-generation guard, toasts, format-command dispatch, divider dragging,
the welcome pane, and the confirm modal. All three remaining v0.4 items add to
it.

Cheapest useful split: move the bibliography loading (`:83-124`, including the
`reloadGeneration` guard and the two `$derived` primitives that exist to defeat
Svelte's object-identity check — a subtlety worth keeping its excellent comment)
into a `lib/bibliography.svelte.ts` rune store, and pull `Toast` and
`ConfirmDialog` into components. That removes most of the churn without a
rewrite.

## Code quality

### Q1. Go is already modern — two nits

`documentservice.go:173`: `recents = append([]string{path}, recents...)` reads
more clearly as `slices.Insert(recents, 0, path)`. `:174-176`: the `if len >
maxRecents` guard is `recents = recents[:min(len(recents), maxRecents)]`.
`documentservice_test.go:46` still uses `for i := 0; i < 12; i++` where
`for i := range 12` now applies. Otherwise the Go is current for 1.25 —
`atomic.Bool`, `slices.DeleteFunc`, and `context.WithCancel` are all used
idiomatically.

### Q2. Silent failures in the settings and recents write paths

`SetPrintOrientation` (`:132-149`) and `addRecent` (`:177-184`) swallow every
error: `MkdirAll`, `Marshal`, and `WriteFile` all just `return`. A user whose
data directory is unwritable gets a menu that silently forgets its state with
no diagnostic anywhere. At minimum log; better, return an error so the frontend
can toast — and since A1 is about to change these signatures anyway, that's the
moment to do it.

### Q3. Frontmatter `bibliography:` paths are unconstrained

`resolveAgainstDoc` (`:194-199`) joins any relative path and honours absolute
ones, so an untrusted `.md` can point the reader — and the 2-second-poll
watcher — at any file on disk. The consequence today is small: the content is
only parsed as BibTeX, and D3's probe confirms nothing reaches the DOM
unescaped. But it belongs alongside the existing backlog item about Vega-Lite
`data.url` fetches, as one third-party-document hardening pass rather than two.

### Q4. The dirty flag is mirrored across the IPC boundary

`App.svelte:68-70` pushes `dirty` to Go through an async binding call; Go's
`WindowClosing` hook reads that mirror (`main.go:71-76`). There's a small window
where ⌘Q immediately after a keystroke sees a stale value. `Save` is also a
second writer on the Go side (`documentservice.go:67`) while the frontend
effect is the first. It's self-correcting in practice — the effect re-pushes —
but the close hook asking the frontend for the answer would remove the class of
bug rather than narrowing the window.

## Testing

### T1. No component or DOM tests

`vitest.config.ts` sets `environment: 'node'` globally; jsdom is installed as a
devDependency but never used. The 116 tests cover the pure libraries genuinely
well (markdownCommands 205 lines of tests, citations 215, charts 164 driving a
fake `EmbedFn`) — but `App.svelte`, `Editor.svelte`, and `Preview.svelte` have
none.

All three remaining v0.4 items are UI behaviour: the welcome-overlay/Open-button
fix, the scroll-sync toggle, and theme switching. Add a jsdom project to the
vitest config (or per-file `// @vitest-environment jsdom`) and drive the first
of them test-first — the welcome-pane bug in particular is a pure
state-and-layout assertion.

### T2. Two regressions this review says are worth pinning

- That citeproc escapes HTML arriving from a `.bib` field, so the
  `innerHTML` path stays safe as the bibliography code evolves.
- Once D3 is fixed, that LaTeX markup in a title renders as text or italics
  rather than literal `<span>` tags — and that `<` and `>` in a title survive.

## Suggested order

**Before v0.4 ships**

1. **P1** — citeproc engine reuse. Biggest user-visible win, and A3 depends on
   it to feel right.
2. **D1** — atomic saves. Highest consequence if it ever fires.
3. **A1** — generalise settings, immediately before adding the theme and
   scroll-sync settings that would otherwise triple the boilerplate. Fold Q2
   into it.
4. **P2** — lazy vega and lazy CSL. Small, local, large payoff.
5. **D3** — bibliography markup fidelity; it's a defect in the v0.3 headline
   feature. Add T2's tests with it.
6. **D2**, **P3**, **Q1** — small and self-contained.

**With the v0.4 features themselves**

- **A3** and **A4** are design input for scroll sync and dark theme rather than
  separate work items. **T1**'s jsdom setup should precede both.

**Defer to v0.5**

- **A2** (service split) and **A5** (App.svelte extraction) — refactors, better
  at a release boundary.
- **Q3** — merge into the existing third-party-document hardening backlog item.
- **P4** — leave until it's observed.
